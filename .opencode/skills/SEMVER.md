# 语义化版本 2.0.0 | Semantic Versioning

> 原文: https://semver.org/lang/zh-CN/

## 摘要

版本格式：主版本号.次版本号.修订号，版本号递增规则如下：

1. **主版本号**：当你做了不兼容的 API 修改
2. **次版本号**：当你做了向下兼容的功能性新增
3. **修订号**：当你做了向下兼容的问题修正

先行版本号及版本编译信息可以加到"主版本号.次版本号.修订号"的后面，作为延伸。

## 版本格式

```
X.Y.Z[-<先行版本>][+<编译信息>]
```

- **X**: 主版本号 (major)
- **Y**: 次版本号 (minor)  
- **Z**: 修订号 (patch)
- **先行版本** (pre-release): 如 alpha, beta, rc
- **编译信息** (build): 如 build.001, exp.sha.5114f85

## 核心规则

### 规则 1: 公共 API 必须定义
使用语义化版本控制的软件必须定义公共 API。该 API 可以在代码中被定义或出现于严谨的文档内。

### 规则 2: 版本号格式
标准的版本号必须采用 `X.Y.Z` 的格式，其中 X、Y 和 Z 为非负的整数，且禁止在数字前方补零。

### 规则 3: 版本发布后不可修改
标记版本号的软件发行后，禁止改变该版本软件的内容。任何修改都必须以新版本发行。

### 规则 4: 初始开发阶段
主版本号为零（0.y.z）的软件处于开发初始阶段，一切都可能随时被改变。这样的公共 API 不应该被视为稳定版。

### 规则 5: 1.0.0 界定公共 API
1.0.0 的版本号用于界定公共 API 的形成。这一版本之后所有的版本号更新都基于公共 API 及其修改内容。

### 规则 6: 修订号递增
修订号 Z（x.y.Z | x > 0）必须在只做了向下兼容的修正时才递增。这里的修正指的是针对不正确结果而进行的内部修改。

### 规则 7: 次版本号递增
次版本号 Y（x.Y.z | x > 0）必须在有向下兼容的新功能出现时递增。在任何公共 API 的功能被标记为弃用时也必须递增。

### 规则 8: 主版本号递增
主版本号 X（X.y.z | X > 0）必须在有任何不兼容的修改被加入公共 API 时递增。

### 规则 9: 先行版本号
先行版本号可以（MAY）被标注在修订版之后，先加上一个连接号再加上一连串以句点分隔的标识符来修饰。

示例：
- `1.0.0-alpha` - 首个先行版本
- `1.0.0-alpha.1` - 第二个 alpha
- `1.0.0-beta` - 测试版
- `1.0.0-rc.1` - 发布候选版

### 规则 10: 版本编译信息
版本编译信息可以（MAY）被标注在修订版或先行版本号之后。

示例：
- `1.0.0-alpha+001`
- `1.0.0+20130313144700`

### 规则 11: 版本优先级

比较版本优先级：
1. 主版本号、次版本号、修订号以数值比较
2. 先行版本号在标准版本之前
3. 数字型标识符比非数字的优先级低

示例：`1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0`

## 递增规则总结

| 变更类型 | 递增 |
|---------|------|
| 破坏性 API 变更 | X (major) |
| 新增功能 (向后兼容) | Y (minor) |
| Bug 修复 (向后兼容) | Z (patch) |
| 弃用功能 | Y (minor) |

## 版本号正则表达式

```
^(?P<major>0|[1-9]\d*)\.(?P<minor>0|[1-9]\d*)\.(?P<patch>0|[1-9]\d*)(?:-(?P<prerelease>(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*)(?:\.(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*))*))?(?:\+(?P<buildmetadata>[0-9a-zA-Z-]+(?:\.[0-9a-zA-Z-]+)*))?$
```
